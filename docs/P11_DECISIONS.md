## ADR-0002: P11 Studio form UI over headless ComfyUI
**Recorded.** 2026-11-02 13:16 CST (Phase 00)
**Context.** The source plan leaves the engine open, leaning to Forge. Its success criteria (one-click templates covering generate → inpaint → background → face, ≤ 5 actions daily) need a layer that owns the multi-step workflow; Forge's UI does not capture that as one template, and the Forge family's upstream maintenance has been uneven. The hardware (8 GB Turing laptop, ~1 GB taken by the desktop) rewards the most memory-efficient engine.
**Options considered.** (a) own form UI over headless ComfyUI; (b) Forge/reForge plus curated extensions and a small templates extension; (c) InvokeAI as-is plus presets and side tools.
**Decision.** (a), owner's choice. P11 owns the UI, recipes, jobs and outputs; ComfyUI is an engine behind an `Engine` interface, reached only on 127.0.0.1. Phase 03 must confirm on the laptop that ComfyUI meets the speed/VRAM/stability criteria; if it fails, Phase 03 stops and asks the owner before switching to the fallback (a Forge-family engine behind the same interface).
**Consequences.** More build work (custom UI, compiler, adapter), but templates, Simple mode and the action targets are fully under P11's control and the engine can be swapped. Engine graph churn is contained in the compiler (ADR-0007).

**Update (2026-11-02 17:56 CST, Phase 03).** **Confirmed** on the laptop: headless ComfyUI v0.43.0 (`426f5ee`) meets every hard requirement of H6. Every candidate model ran at its native bucket without OOM inside the 8 GB card (peak 7.7 GB total including the ~1.1 GB desktop, by ComfyUI's dynamic VRAM; 6.5 GB with it disabled), the default combination passed 50 consecutive 2560×1440 runs with no failure, and the torch build runs real fp16 kernels on sm_75. No fallback engine was installed or measured, since H6 only allows a switch when ComfyUI fails. Evidence: `docs/P11_BENCHMARKS.md`.

## ADR-0005: Unfiltered generation; NSFW guard kept on face-swap
**Recorded.** 2026-11-02 13:16 CST (Phase 00)
**Context.** The owner requires no software-imposed content restrictions on generation. Face-swap combined with unfiltered generation can produce sexual imagery of real, identifiable people, which is harmful and illegal to distribute in many jurisdictions.
**Options considered.** No guard anywhere; guard on generation and face-swap; guard on face-swap only.
**Decision.** No safety checker or prompt filter on generation (owner requirement). The face-swap and video face-swap paths keep an NSFW check on the target and refuse sexual or nude targets; no feature, preset or template places a real person's face into sexual content; nothing sexualizes minors. Fixed by the planning session (spec S5), not a user setting.
**Consequences.** Phases 12 and 13 implement and test the guard; Phase 16 verifies it cannot be bypassed through templates or the API. Jokes, avatars and logos are unaffected.

## ADR-0007: Templates are versioned P11 recipes compiled to engine graphs
**Recorded.** 2026-11-02 13:16 CST (Phase 00)
**Context.** Templates must capture full multi-step state and survive engine updates.
**Options considered.** Store ComfyUI workflow JSON; store P11 recipes and compile.
**Decision.** Recipes (spec R6) with a schema version and migrations; a pure compiler emits ComfyUI API graphs.
**Consequences.** Engine node changes touch only the compiler; recipes stay readable and diffable; the compiler needs strong tests (Phase 04).

**Update (2026-11-02 18:28 CST, Phase 04).** Schema v1 is implemented in `src/p11/recipe/model.py` (frozen Pydantic v2 models, `extra="forbid"`, tuples for collections): `Recipe {schema_version: 1, id, name, tags, folder, steps, slots, seed, created_at (timezone-aware), source_image?: FileRef}`; `Step` is a union discriminated by `type`: `generate` (prompt, negative, style, aspect, model, vae, loras, sampler overrides, chain, quality, batch_size), `upscale` (image_slot, chain model/latent/both, scale or width+height, upscaler, model, denoise, prompt, negative), `inpaint`, `replace_background`, `face_swap`, `pose`, `reference`, `text_overlay` (fields fixed now; bodies compiled by Phases 10–14). `ModelRef {manifest_id, sha256?}`, `FileRef {ref, sha256?}` (opaque P11 file ID, no `..`), `Slot {name, kind: text|image|face_image|background_image|mask|video, label, required, default (text only)}`, `SeedStrategy = fixed(value) | random | increment(start)`. Text fields reference text slots as `{{name}}`. Migrations live in `recipe/migrate.py` (`MIGRATIONS[n]: v n → v n+1`; future versions refused with "Update P11"). Compiler details in ADR-0019.

## ADR-0009: Turing defaults: fp16, SDPA, fp16-safe SDXL VAE, sm_75-capable torch
**Recorded.** 2026-11-02 13:16 CST (Phase 00)
**Context.** RTX 2070 Mobile is compute capability 7.5; host driver 615.78.08 (nvidia-open), CUDA 13.4. Newer CUDA toolkits have dropped older architectures, so the torch build must be checked for sm_75.
**Options considered.** Recorded by Phase 03 (which CUDA build of torch; SDPA vs xformers; fp16 vs fp32 VAE).
**Decision (Proposed).** fp16 UNet/text encoders, SDPA attention, fp16-safe SDXL VAE, a torch build verified to run kernels on sm_75 with this driver.
**Consequences.** Phase 03 pins the exact versions in `engine/engine.lock.toml` and marks this Accepted.

**Update (2026-11-02 17:56 CST, Phase 03).** **Accepted** with these measured details:
- torch 2.14.1+cu130 / torchvision 0.29.1+cu130 from `https://download.pytorch.org/whl/cu130` (cuDNN 9.24). `sm_75` is in `torch.cuda.get_arch_list()`, and `scripts/engine_setup.sh` runs an fp16 matmul, a conv and SDPA on the GPU with warnings as errors. torch 2.15.0 was skipped because it was under two weeks old at pin time.
- UNet and text encoders run fp16. Attention is PyTorch SDPA (ComfyUI logs "Using pytorch attention"); xformers is not installed.
- ComfyUI decodes the VAE in **fp32** on Turing by default (no bf16), so the fp16-fix SDXL VAE (`madebyollin/sdxl-vae-fp16-fix`) is not needed for correctness. It is kept as the explicit VAE for RealVisXL, which ships without a reliable baked VAE, and it allows a later `--fp16-vae` speed test (follow-up). Wallpaper decodes use `VAEDecodeTiled` (512 px tiles).
- Dynamic VRAM (the v0.43.0 default, `comfy-aimdo`) is kept: same speed as `--disable-dynamic-vram`, up to 10 % faster on the upscale chain; see ADR-0018 for the VRAM mode.

## ADR-0010: Wallpaper presets = native bucket + upscale
**Recorded.** 2026-11-02 13:16 CST (Phase 00)
**Context.** Models degrade (duplicated subjects, composition errors) far from their training resolution; 1920×1080 and 2560×1440 exceed SDXL's ~1 MP sweet spot and VRAM budget.
**Options considered.** Direct generation; native bucket + latent/hires pass; native bucket + model upscaler; tiled upscale.
**Decision (Proposed).** Native-bucket generation then an upscale chain chosen by Phase 03 measurements (quality/speed toggle in Phase 14).
**Consequences.** Presets carry both the generation size and the output size; the compiler emits the chain.

**Update (2026-11-02 17:56 CST, Phase 03).** **Accepted.** The default chain for both wallpaper presets is **`model`**: native bucket 1344×768 (SDXL) → 4×NomosWebPhoto RealPLKSR → Lanczos resize to 1920×1080 or 2560×1440. It adds only ~5 s to the base image (RealVisXL Lightning: 18.3 s at 1920×1080, 18.7 s at 2560×1440, warm), compared with 45–66 s for `latent` (bislerp latent upscale + hires KSampler at denoise 0.45) and 55–88 s for `both` (model upscale + VAE re-encode + hires pass at denoise 0.3). At 1:1 crops the model chain is crisp; a refinement pass adds real generated detail at 3–5× the time, so it is the **Quality** option of Phase 14's toggle. Provisional Quality chain: `latent` (denoise 0.45, about half the base steps, tiled VAE decode), the faster of the two refinement chains; both ran without OOM at both presets. Phase 14 makes the final Quality pick between `latent` and `both` when it tunes prompt defaults, using these numbers. Direct generation at wallpaper size was not run (R3). The upscaler is 4×NomosWebPhoto RealPLKSR (CC-BY-4.0) rather than 4x-UltraSharp (CC-BY-NC-SA-4.0), as the two looked alike and H3 prefers the permissive one.

## ADR-0012: Installer: clone + `./install.sh`, no driver installs
**Recorded.** 2026-11-02 13:16 CST (Phase 00)

## ADR-0017: gitleaks as a local pre-commit hook from a pinned user-level binary
**Recorded.** 2026-11-02 15:08 CST (Phase 01)
**Status.** Accepted
**Context.** Phase 01 asks for a gitleaks pre-commit hook with a pinned rev, and spec H4 forbids sudo/pacman. The upstream `gitleaks` pre-commit hook builds from source and needs a Go toolchain on every contributor's machine.
**Options considered.** Upstream hook repo (`rev` pin, needs Go); `language: system` hook calling a pinned binary; gitleaks-action only in CI.
**Decision.** `.pre-commit-config.yaml` uses a `language: system` hook calling `gitleaks` 8.30.1 from `PATH`, installed at user level from the release tarball after checking its SHA-256 against the release checksums. CI installs the same version with its SHA-256 checked in the workflow and scans full history. The basic hooks use `pre-commit-hooks` v6.0.0 (tag verified at its repo 2026-11-02 15:08 CST).
**Consequences.** Contributors must install gitleaks themselves (documented in CONTRIBUTING); version drift between machines is possible but CI is the backstop. Dependabot does not track the binary; bump it by hand with its new SHA-256.

## ADR-0019: Recipe compiler: one graph per step, modifier steps, placeholder inputs, raw PNG chunks
**Recorded.** 2026-11-02 18:28 CST (Phase 04)
**Status.** Accepted
**Context.** Phase 04 builds the pure recipe → ComfyUI compiler (ADR-0007) and the output metadata. Multi-step recipes (generate → inpaint → background → face → upscale) must compile now for generate/upscale and stay open for Phases 10–14; some later steps (text overlay, possibly compositing) do not run in the engine.
**Options considered.** (a) One merged graph per recipe; (b) one graph per graph-producing step, images passed between graphs by the job runner. Pose/reference as (c) their own graphs or (d) modifiers folded into the generate step. PNG metadata via (e) Pillow re-save with `PngInfo` or (f) editing chunks in the byte stream.
**Decision.**
- **(b) One `EngineGraph` per graph-producing step.** A later step reads the earlier output through a `LoadImage` node whose `image` is a placeholder (`p11:step:<i>`, `p11:slot:<name>`, `p11:source`), listed in `EngineGraph.inputs`; the job runner uploads the file and substitutes the engine's name. Each step's output is saved, indexed and resumable on its own, non-engine steps can sit between engine steps, and a failure points at one step. Cost: one PNG upload per later step (small next to sampling time).
- **(d) `pose` and `reference` are modifiers**: they must follow a `generate` step and are folded into its graph through `register_modifier(type, fn)`, which rewrites the step's `Conditioning` (model, clip, vae, positive, negative). Graph steps register with `register_step(type, fn)`; unregistered types raise `UnsupportedStepError` naming the phase that adds them.
- Graphs use core nodes only, with class and input names read from ComfyUI v0.43.0 (`426f5ee`): `CheckpointLoaderSimple, VAELoader, LoraLoader, CLIPSetLastLayer, CLIPTextEncode, EmptyLatentImage, KSampler, VAEDecode, VAEDecodeTiled, VAEEncodeTiled, LatentUpscale, LatentUpscaleBy, UpscaleModelLoader, ImageUpscaleWithModel, ImageScale, ImageScaleBy, LoadImage, SaveImage`. Output is `SaveImage` (`filename_prefix p11/step-NN`); the job runner moves it into the R7 layout. Node IDs are sequential and JSON is canonical (sorted keys), so the same input gives byte-identical graphs.
- Sampler and scheduler names are checked at compile time against the pinned engine's lists, not in the schema, so an engine bump never invalidates stored recipes.
- Models are resolved through a `ModelRegistry` protocol (Phase 06 implements it from the manifest); `PROVISIONAL_DEFAULT_SET` carries ADR-0018's IDs, files, hashes and sampler defaults until then. A `ModelRef.sha256` that differs from the registry's is an error.
- Seeds are stored up to 2^53 − 1 (JavaScript-safe); random seeds are drawn below 2^32 by the runner (`resolve_seed`) and passed in, so `compile` itself stays pure. The hires pass uses seed + 1 (as in the bake-off).
- Slot kind `mask` was added to the kinds in the phase prompt so inpaint masks and manual background masks are typed inputs.
- **(f) PNG chunks are edited in the byte stream**: `iTXt` chunks `p11:recipe` and `p11:run` (zlib) are inserted before `IEND`, so pixels are never re-encoded; `strip_metadata` keeps only image, colour and transparency chunks (drops all text, `eXIf`, `tIME`, ComfyUI's `prompt`/`workflow` and unknown chunks).
- Pydantic v2 and stdlib `sqlite3` (FTS5, migrations on `PRAGMA user_version`) follow R21; no deviation. Hypothesis (MPL-2.0, dev only) was added for property tests.
**Consequences.** Phase 05/07 must feed `EngineGraph.inputs` and collect `SaveImage` outputs; Phase 06 implements `ModelRegistry`; Phases 10–13 add `register_step`/`register_modifier` compilers; Phase 14 (text overlay) and possibly 11 (compositing) must extend the driver with a local, non-engine step kind and an ADR. Compiler changes are guarded by 20 golden graphs (`tests/golden/compile/`, regenerate with `P11_UPDATE_GOLDEN=1` and review the diff).

## ADR-0020: Engine adapter: one protocol, supervised ComfyUI, sticky low-VRAM OOM retry, NVML telemetry
**Recorded.** 2026-11-02 19:26 CST (Phase 05)
**Status.** Accepted
**Context.** Phase 05 puts every engine call behind `p11.engine.Engine` (ADR-0002) with a real implementation over the pinned ComfyUI v0.43.0 (`426f5ee`) and a fake for tests. It must recover from OOM (R5, ADR-0018), supervise the process (R14), hold the GPU lock (R24, ADR-0014), stay on loopback and offline (S1) and report GPU telemetry at ≤ 1 Hz (R19).
**Options considered.** Telemetry: (a) NVML through `nvidia-ml-py`, (b) `nvidia-smi` CSV parsing, (c) `pynvml` (the deprecated third-party wrapper of the same name). After an OOM retry: (d) stay in low-VRAM mode, (e) restart back to dynamic VRAM straight away. Run API: (f) a single async `run(graph, on_event)` per job with its own websocket, (g) one long-lived websocket multiplexing all jobs. Forced OOM in tests: (h) an oversized latent, (i) a second process holding most of the VRAM.
**Decision.**
- **(a) with (b) as fallback.** `nvidia-ml-py` 13.615.71 is NVIDIA's official binding (BSD-3-Clause, pure-Python `py3-none-any` wheel over the driver's `libnvidia-ml`; checked on PyPI 2026-11-02 18:50 CST); it reads memory (v2 info, excluding reserved), temperature, power, SM/memory clocks and clock-event (throttle) reasons without a subprocess per sample. If NVML does not initialise, `nvidia-smi --query-gpu` is parsed instead; with neither, telemetry is `None`. `ThermalGuard(pause_at, resume_at)` is a two-state machine with hysteresis; settings default to 87 / 80 °C (owner question 5, H9), validated `resume < pause`.
- **(d) sticky low-VRAM.** `run_with_oom_retry` frees memory (`/free` with `unload_models`), restarts the engine with `--disable-dynamic-vram --lowvram` (ADR-0018) and retries once; a second OOM raises `EngineOOM` with a plain-English message and hint. The engine stays in low-VRAM mode (~10 % slower, ADR-0018) because the restart back costs a model load and similar jobs tend to follow; the job queue (Phase 07) may call `restart("dynamic")` when idle.
- **(f) one websocket per run**, opened before `POST /prompt`, with a client-chosen `prompt_id` (UUID) so every message is filtered exactly; runs are serialized by a lock (the engine runs one prompt at a time anyway). Outputs are fetched through `/history` + `/view` into memory, then deleted from the engine's scratch output directory and history (S6); P11 writes its own copy (Phase 07).
- **Supervisor.** `ProcessSupervisor` starts the command in its own session with `PR_SET_PDEATHSIG = SIGTERM` (no orphaned engine if P11 dies), logs to `~/.cache/p11/logs/engine.log` (rotated at 10 MB, 3 kept), waits for `/system_stats`, refuses a second instance (pid file `~/.cache/p11/engine.pid` checked against `/proc/<pid>/cmdline`, plus a port probe), restarts once after an unexpected exit and then gives up and releases the GPU lock; stop is SIGTERM to the process group, SIGKILL after 30 s. `start()` refuses an engine whose `/system_stats` version differs from `engine.lock.toml` or that is not bound to 127.0.0.1. The engine environment sets `HF_HUB_OFFLINE`, `HF_HUB_DISABLE_TELEMETRY`, `TRANSFORMERS_OFFLINE`, `DO_NOT_TRACK`, `COMFYUI_DISABLE_PRODUCT_TIPS` on top of the lock's `--offline` flags.
- **(i) for the real forced OOM.** ComfyUI v0.43.0 does not fail on oversized latents on this card: 3072² and 4096² latents ran past a 240 s timeout and batch 8 at 1024² finished in 93 s (it splits batches and offloads with dynamic VRAM; probed 2026-11-02 19:00 CST). A helper process that leaves 600 MiB of VRAM free makes the SDXL `VAEDecode` raise a real CUDA OOM (1500 MiB still fits). The gpu tests cover both outcomes: pressure relieved when the retry starts → recovers in low-VRAM mode; pressure kept → the plain-English error. The FakeEngine models OOM by latent area per VRAM mode.
**Consequences.** Nothing outside `p11.engine` imports `p11.engine.comfy`; Phase 07 gets the engine from `p11.engine.create_engine(settings, fake=…)` and should wrap runs in `run_with_oom_retry`. `p11 serve --fake` puts a `FakeEngine` on `app.state.engine`. The installer (Phase 15) must place `engine.lock.toml` under `~/.local/share/p11/engine/` (or set `P11_ENGINE_LOCK`) for a non-repo install. Measured on the laptop: adapter overhead −0.7 % to +3.5 % against the Phase 03 bench client (order-dependent, within noise), interrupt 0.52 s, engine start 5.6 s (docs/P11_BENCHMARKS.md).

## ADR-0021: Model manager: manifest v1, verified downloader, separate state files, join by hash
**Recorded.** 2026-11-02 23:09 CST (Phase 06)
**Status.** Accepted
**Context.** Phase 06 turns ADR-0006 and ADR-0018 into code: a hash-pinned `models/manifest.toml`, a resumable verified downloader (R9, S9), licence acknowledgements (H3), the S4 format policy for user models, a registry for the compiler (ADR-0019) and `p11 models`. The phase prompt fixes the field list; some details needed choices.
**Options considered.** State: (a) write enable/disable flags and user models into `config.toml`, (b) separate files P11 owns. Status hashing: (c) hash every file on every `list`, (d) size check only, (e) a SHA-256 cache keyed by path, size and mtime with a forced re-hash in `verify`. Redirects: (f) let httpx follow them, (g) follow them by hand. Test downloads: (h) a TLS test server with a throw-away CA, (i) plain http to 127.0.0.1 behind explicit test-only switches.
**Decision.**
- **Manifest schema v1** (`src/p11/models/manifest.py`, frozen Pydantic, `extra="forbid"`): the prompt's fields plus `name`, `source` (repo @ commit, for people), `scale` (upscalers; required for them and only for them) and `licence.commercial_use` (the H3 "commercial use allowed?" flag, kept apart from `flags`: `non-commercial | attribution | use-restrictions | share-alike | research-only`). `base` also accepts `any` (upscalers). `files` holds exactly one file in v1. Kind `facedetect` (folder `facedetect/`) is added for Phase 12. Validation also rejects: duplicate IDs, two entries writing one file, a `defaults.vae` that is not a VAE in the manifest or not in every set of its checkpoint, a login-only entry in `default` (H2), `commercial_use = true` with `non-commercial`, non-HTTPS URLs and file names with path parts. A licence needs an acknowledgement when it has flags or does not allow commercial use (MIT needs none). URLs name the Hugging Face commit (`/resolve/<sha>/`), so a host-side change cannot swap the file. `full` includes `default`.
- **(b) separate state files:** `~/.config/p11/licences.toml` (acknowledgements with a `YYYY-MM-DD HH:MM TZ` timestamp and how they were given; a licence-name change asks again) and `~/.config/p11/models.toml` (disabled IDs, user models), written atomically with mode `0600`, so P11 never rewrites the hand-edited `config.toml`.
- **(e) hash cache** `~/.cache/p11/model-hashes.json`: `list`, `install` and `doctor` re-hash only files whose size or mtime changed; `p11 models verify` always re-hashes. A second `install default` therefore reads nothing and downloads nothing.
- **(g) manual redirects**, at most 10, each hop HTTPS (or allowed loopback http), with the `Authorization` header added per hop only when the hop's host equals a token's host. Hugging Face answers `/resolve/` with a 302 to its CDN (`us.aws.cdn.hf.co`, checked 2026-11-02 23:09 CST), so a token never reaches the CDN. Tokens come from `~/.config/p11/secrets.toml` `[tokens] "host" = "…"`, which is refused if group/other can read it; no token exists in the build (H2).
- **Downloader:** streams into `<file>.part` with SHA-256 computed on the fly (an existing `.part` is hashed first, then resumed with `Range`); 200 instead of 206 restarts from 0; 416 or a wrong `Content-Range` discards the part; more bytes than the manifest size, or a final hash mismatch, deletes the part and fails; 429/5xx/transport errors retry with exponential backoff (2, 4, 8, 16 s); 401/403/404 fail at once with a hint. A pre-flight disk check needs the remaining bytes plus 1 GiB per filesystem; ENOSPC during the write keeps the part for a resume. At most 2 concurrent downloads per host.
- **Join by hash:** a curated model's file under another name in its folder counts as installed (the compiler gets the real file name), and `p11 models add` of a file whose hash is a manifest entry installs it as that entry. Other files in model folders are listed as `unregistered`.
- **User models (S4):** format sniffed from content (safetensors header, `GGUF` magic, pickle protocol bytes, PyTorch zip with a `.pkl`); pickle formats refused without `--allow-pickle`, which prints the risk; anything unrecognised is refused. Kind and base are detected from safetensors tensor names (checked against the six curated files) or given with `--kind`. Files are copied by default, `--link` symlinks. Removal unregisters and leaves the file unless `--delete-file`; a curated model's `remove` deletes its file (with `--yes` or a prompt). User checkpoints get P11's family defaults (`dpmpp_2m`/`karras`, SDXL 30 steps CFG 5, SD 1.5 25 steps CFG 6), not facts about the model.
- **`install --from DIR`** reuses already-downloaded files (hard link, else copy) after checking size and hash, for Phase 15's throw-away-HOME install (H1).
- **(i) loopback http for tests:** `Downloader(insecure_hosts=…)` accepts only loopback names, and `parse_manifest(..., loopback_http=True)` only `http://127.0.0.1`; neither is reachable from the CLI or the app. The one real-network test (`tests/net/`, `slow`) runs only with `P11_NET_TESTS=1`, so CI and `make check` stay offline.
- `p11.recipe.registry.PROVISIONAL_DEFAULT_SET` stays as the compiler tests' pure registry; a test asserts it equals the manifest. The app's registry is `ModelManager.registry()`, which raises `UnknownModelError` with a `p11 models install …` hint for missing, corrupt or disabled models.
**Consequences.** Phase 07 uses `ModelManager.from_settings().registry()` for compiles, `p11.models.check()` (a list of `p11.problems.Problem`) in `p11 doctor`, and `statuses()`/`as_json()` for `GET /api/models`. Phase 14's Models page reads the same JSON as `p11 models list --json`. Phases 10–12 add entries with this schema and must keep the `default` set within 30 GB. Phase 15 calls `p11 models install <set> [--accept-licences] [--from DIR] --json`, places `models/manifest.toml` at `~/.local/share/p11/manifest.toml` (or sets `P11_MODEL_MANIFEST`) for a non-repo install, and can rely on `install` rewriting `extra_model_paths.yaml` when the engine directory exists.

## ADR-0022: Studio API: launch-code sessions, SSE events, one GPU worker with an idle engine stop
**Recorded.** 2026-11-02 23:48 CST (Phase 07)
**Status.** Accepted
**Context.** Phase 07 turns ADR-0013 (local-only posture) and spec S1/S2/S6/S8 into the Studio API, and adds the job queue and CLI lifecycle over the Phase 05 engine adapter. The prompt asks for decisions on the event transport and the token handling; several other details needed choices.
**Options considered.** Events: (a) a websocket, (b) server-sent events. Token delivery: (c) the session token itself in the URL fragment, (d) a one-time launch code in the fragment, traded for the token. Browser credentials: (e) header only, (f) cookie only, (g) header for everything plus an `HttpOnly` cookie accepted for safe methods. Uploads: (h) multipart (`python-multipart`), (i) the raw file as the request body. Engine lifetime: (j) start with the Studio, (k) start on the first job and stop when idle.
**Decision.**
- **(b) SSE** at `GET /api/events` with FastAPI's built-in `EventSourceResponse` (keep-alive pings included): the stream is one-way (server → browser), works with `EventSource` and the cookie, reconnects by itself with `Last-Event-ID` (a 256-event replay buffer, previews excluded), and needs no websocket handling in the security middleware, which refuses websockets outright. Every event has a strictly increasing ID, so order is the publish order; slow clients lose their oldest `progress`/`preview`/`gpu` events before any `job` or `image` event.
- **(d) launch codes.** Each `p11 serve` makes a random 256-bit token, written `0600` to `$XDG_RUNTIME_DIR/p11/studio.token`. `p11 open` uses it to ask `POST /api/session/launch` for a one-time code (valid 2 minutes) and opens `http://127.0.0.1:<port>/#launch=<code>`. The page posts the code to `POST /api/session` (the only `/api` route without a token), gets the token, keeps it in `sessionStorage` and removes the fragment. The browser's command line (readable in `/proc`) therefore only ever holds a spent code. Token and codes are registered with the log redactor.
- **(g)** `/api` needs `Authorization: Bearer <token>` (or `X-P11-Token`); the `p11_session` cookie (`HttpOnly; SameSite=Strict; Path=/`) is accepted only for `GET`/`HEAD`, so `<img src="/api/images/…">` and `EventSource` work while a forged state-changing request never does. In front of that: a Host allowlist (`127.0.0.1:<port>`, `localhost:<port>`; 421 otherwise) against DNS rebinding, and a refusal of a foreign `Origin` or cross-site `Sec-Fetch-Site` on state-changing requests and on all `/api` reads. No CORS headers are ever sent. CSP `default-src 'self'` with `img-src 'self' blob: data:`, `object-src 'none'`, `frame-ancestors 'none'`, plus `nosniff`, `no-referrer`, `X-Frame-Options: DENY`, COOP/CORP and `Cache-Control: no-store` on `/api`. The OpenAPI schema is at `/api/openapi.json` behind the token; no docs UI (it would load remote scripts). FastAPI 0.162's native OpenTelemetry hooks are switched off explicitly.
- **Size caps** in the middleware: 1 MiB for JSON routes and template imports, 1 GiB for `/api/uploads`, enforced on `Content-Length` and on the streamed body (413 either way); the upload route then applies the per-kind caps (64 MiB images, 1 GiB videos).
- **(i) raw-body uploads** (`POST /api/uploads?kind=image|mask|video`): no multipart parser dependency. Images are fully decoded by Pillow (PNG/JPEG/WebP only, 40 MP cap), turned upright and re-encoded as PNG without EXIF; videos are probed by ffprobe (container and codec allowlists; hard caps 600 s and 2160p; the R13 60 s / 1080p limits are settings that only warn) and remuxed with `-map_metadata -1` so MP4 location tags never reach disk. Names are generated (`img-<hex>`, `vid-<hex>`); the ID is matched against a strict pattern before any path is built. A binding names an upload (`{"ref": "img-…"}`) or an earlier gallery image (`{"ref": "gallery/<id>"}`).
- **(k) one GPU worker.** An asyncio queue runs jobs in order; the engine is started for the first job (the supervisor takes the GPU lock then) and stopped after `engine_idle_stop` seconds without jobs (default 300), which frees the lock for other sessions. After an OOM retry left the engine in `lowvram`, the worker restarts it in `dynamic` mode once the queue has been idle for 60 s (and a stopped `lowvram` engine is started in `dynamic`), so one oversized job does not slow every later one (ADR-0020's open question). Jobs are validated at submit time by compiling with seed 0 and resolving every bound file, so slot, model and file errors are 4xx responses, not failed jobs. A job is a recipe, its bindings and a `count` (1–16 runs, run *i* seeded by the recipe's strategy); every step output is saved, embedded and indexed, and step *i*'s `parent` is step *i−1*'s first image. Jobs live in `~/.local/share/p11/jobs.db`; at startup every job left `queued`, `running` or `paused` becomes `failed` with `job.interrupted`. Long jobs (more than one graph) check the `ThermalWatch` between graphs and sit in `paused` above 87 °C until 80 °C (H9); Phase 13 calls `JobControl.checkpoint(long=True)` per batch.
- **Errors** are one JSON shape everywhere, `{"code", "message", "hint"}`, from `p11.jobs.errors.problem_for` (e.g. `models.missing` 409 with `p11 models install default`, `engine.oom` with the R5 message, `gpu.busy` naming the lock holder).
- **Logging:** JSON lines in `~/.cache/p11/logs/studio.log` (5 MB × 3, `0600`); uvicorn's access log is off (it carries query strings such as gallery search text) and P11 logs method, path, status and duration instead; prompt text and bindings are logged only through `debug_private` at DEBUG; registered secrets are redacted at every level, including tracebacks.
- **Lifecycle:** `p11 start` runs `python -m p11 serve` detached and waits for `/healthz`; `serve` writes `studio.json` (pid, port, mode) next to the token; `stop`/`status`/`open` check that the pid's command line is a `p11 serve` before using or signalling it. `p11 open` uses Omarchy's `omarchy-launch-webapp` when present (the same app-mode window as Omarchy web apps, through the default browser), else a Chromium-family browser with `--app=`, else `xdg-open`; `$P11_BROWSER` overrides. `p11 serve --fake` keeps its demo gallery in `~/.cache/p11/fake/` so it never mixes with real outputs.
**Consequences.** Phase 08 builds on `frontend/src/api/session.ts` (`bootstrapSession`, `api`), the `/api` routes and the SSE event types listed in `docs/P11_ARCHITECTURE.md`; it never puts the token in a URL. Phases 10–13 add routes under `src/p11/api/routes/` (they get the middleware for free) and feed images through `Runner.resolve_file`. Phase 13 uses `kind=video` uploads and the thermal checkpoint. Phase 15's desktop entry runs `p11 open`. Phase 16's threat model starts from the middleware and the upload validators. Dev dependency `httpx2` (BSD-3-Clause) replaces the deprecated httpx path of Starlette's `TestClient`.

## ADR-0024: Templates: server-side capture with slot inference, starter install marker, mark-only logo starters until Phase 14
**Recorded.** 2026-11-03 04:37 CST (Phase 09)
**Status.** Accepted
**Context.** Phase 09 makes any result a reusable template in at most three actions and ships starter templates. It needed choices on where the template is derived from a run, how slots are inferred, how starters are installed without resurrecting deleted ones, and what the logo starters do while the text overlay (Phase 14) does not exist.
**Options considered.** Capture: (a) build the template recipe in the browser from the run record, (b) a server route that reads the run record and returns the saved template. Slots: (c) ask the user to tick each value, (d) infer from the run. Starters: (e) copy missing starter files at every start, (f) install each starter ID once and remember it. Logo starters: (g) include a `text_overlay` step now, (h) leave the step out until Phase 14 and tag them.
**Decision.**
- **(b)+(d)** `POST /api/templates/from-image {image_id, name, folder, tags, seed: fixed|random, variable_prompt}` calls the pure `p11.templates.capture.capture_template(record, …)`. Bound uploads are never copied into a template (S6). The whole chain of `RunRecord.recipe.steps` is kept. - **(f)** `p11.templates.starter.install_starters` reads `templates/starter/*.json` (override `$P11_STARTER_TEMPLATES`), installs each starter whose ID is not in the marker `<templates>/.starter-installed.json` and not already in the store, and records it. A starter the user deleted or edited is never restored or overwritten. Only `p11 serve` installs them (`create_app(starters=True)`); tests and the API factory default to off.
- **(h)** The compiler rejects `text_overlay` until Phase 14, so a logo starter with that step would not run. The three logo starters therefore make the mark only, carry the tag `mark-only` (the card says "text on the logo arrives with the text overlay (Phase 14)") and use a `symbol` or `emblem` text slot. Run with open required slots shows the slot form; remembered inputs (`localStorage` `p11.slot-memory`, upload IDs and text only, never file contents) let a second run take one click; the last five templates run are chips in Generate, and Ctrl+K opens a fuzzy palette. ## ADR-0025: Inpainting: core-node graph, P11-side mask prep and crop-and-stitch, additive Inpaint fields, inline fixed masks
**Recorded.** 2026-11-03 05:18 CST (Phase 10)
**Status.** Accepted
**Context.** Phase 10 makes inpainting first-class: a mask editor, an Inpaint view, the `inpaint` compiler step, "only masked area at full resolution", tuned presets, and templates that capture the mask. It needed choices on the inpaint nodes, where mask processing and crop-and-stitch happen, how the Phase 04 `Inpaint` fields grow, how a template keeps a mask, and whether a dedicated inpaint model is worth adding.
**Options considered.** Graph: (a) `VAEEncodeForInpaint` (grey fill, needs denoise 1.0), (b) `VAEEncode` + `SetLatentNoiseMask`, (c) `InpaintModelConditioning` with its noise mask. Mask prep and crop: (d) core nodes (`GrowMask`, `ImageBlur`, crop nodes) in the graph, (e) a custom crop-and-stitch node, (f) P11 does it around the graph (`media/`). Schema: (g) bump to schema v2 with a migration, (h) add optional fields with defaults to v1. Fixed mask in a template: (i) keep the upload reference, (j) a template asset file next to the JSON, (k) the mask inline in the step as a small PNG. Model: (l) add a dedicated SDXL inpaint checkpoint, (m) use the base model.
**Decision.**
- **(c)** `InpaintModelConditioning` (`noise_mask=True`) → `KSampler` (title `inpaint`) → `VAEDecode` → `ImageCompositeMasked` over the input with the same mask. It works for any denoise, keeps the original colours under the mask as a starting point, and feeds a dedicated inpaint model's extra channels if one is used later. Core nodes only (S3), all already in `FakeEngine.KNOWN_NODES`; names read from ComfyUI `426f5ee`.
- **(f)** The compiler stays pure: it records a `MaskPrep` on `EngineGraph.prep`, and the runner calls `p11.media.inpaint.prepare` before upload and `stitch` on the result. `prepare` resizes the mask to the image, grows (box blur + threshold) and blurs (Gaussian) it at full resolution, and with `crop` cuts the soft mask's box plus padding and scales it to ~1 MP (≤ 4×; capped at 2560×1440); `stitch` scales back and blends over the **original** with the soft mask, so unmasked pixels are byte-identical (tested on the FakeEngine and the real engine). Graph-side masks would have needed the crop box at compile time (it depends on mask pixels) or a custom node (an ADR and a pin, S3).
- **(h)** New optional fields `mask_png`, `mask_blur_px` (12), `crop` (true), `padding_px` (48), `sampler`; `mask_slot` becomes optional with "exactly one of `mask_slot`/`mask_png`". Every older v1 document still validates (tested), and no stored recipe could contain a compiled inpaint step before this phase, so a version bump and migration would add nothing. `denoise_preset` (`subtle|balanced|major`, UI *Subtle fix / Change / Replace*) overrides `denoise` with `presets.INPAINT_PRESETS`.
- **(k)** `POST /api/templates/from-image {mask: slot|fixed}`: *fixed* (the dialog's default for inpaint images) stores the run's mask as a greyscale PNG ≤ 1024 px long side, base64 in `mask_png` (≤ 400 000 characters; typically a few KB), compiled to an `inline` `GraphInput`. A mask is a shape, not a photo, so S6 is kept (photos still become slots); the template stays one portable JSON file for export/import. *slot* keeps a `mask` slot.
- **Presets** from 70 runs on 10 images (`docs/P11_BENCHMARKS.md` → Inpainting): Subtle fix 0.4, Change 0.65, Replace 0.85; crop on by default (~12 s per fix at 1920×1080 vs ~32 s full frame, and full frame at 0.6 barely changes small regions).
- **(m)** No inpaint-specific model: the base model with a noise mask gave usable results at every preset with no OOM (peak 7.7 GB), and a dedicated SDXL inpaint checkpoint would be a further multi-GB download outside the measured default set (not measured here; a follow-up if quality ever needs it). The manifest is unchanged.
- **Mask editor:** image-sized mask canvas under a CSS transform; per-stroke layer recomposited only in the dirty box (snapshot + layer at the stroke's opacity), history replay for undo. 60 fps on 2560×1440 in Chromium. Hand-off between views through `NavProvider.edit(view, image)`.
**Consequences.** Phase 11 reuses `MaskEditor` (adding an initial-mask prop for the auto-mask) and may reuse `MaskPrep`/`stitch` for its blend; Phase 12 can reuse the crop-and-stitch for face detail; Phase 14's logo "refine" opens Inpaint. A replaced face can show a soft seam where skin tones differ (recorded as a follow-up: optional colour matching in `stitch`). Outpainting stays out of scope.

## ADR-0027: Local-step driver: `LocalStep` plan items with an optional engine tail
**Recorded.** 2026-11-03 09:05 CST (Phase 11)
**Status.** Accepted
**Context.** Background replacement is mostly not engine work: segmentation, colour matching, edge decontamination and blending have no ComfyUI core-node equivalent (colour transfer needs LAB statistics), while its harmonize pass is an ordinary inpaint graph. ADR-0019 made `compile()` return one engine graph per step, so a step that mixes local work and engine work had no home; Phase 14's `text_overlay` is local-only and was waiting on the same extension.
**Options considered.** (a) Express compositing with engine nodes and a custom node for colour match (S3); (b) an engine-only step whose graph is wrapped by P11-side `prep`/`stitch` hooks (the Phase 10 `MaskPrep` pattern) with no local-only case; (c) a local-step kind in the driver; (d) compile one plan item per sub-step of a step (a flat chain with implicit intermediate outputs).
**Decision.**
- **(c)+(d) `compile()` returns `list[PlanItem]`, `PlanItem = EngineGraph | LocalStep`.** A `LocalStep` is pure data: `op` (a `p11.media` entry point), pure JSON `params`, `GraphInput`s (whose placeholder doubles as the operation's input name), model IDs and an optional `engine` tail graph. The runner resolves the inputs exactly like graph inputs, runs the op in a worker thread (`asyncio.to_thread`), and keeps its named outputs (`image`, `mask`) for the tail's `GraphInput.source == "local"` inputs (`p11:local:<name>`) and for the save path. One step compiles to one item, or to a local step plus its engine tail. Only a step's **last** plan item is saved and becomes the next step's input; intermediate items (the composite before the harmonize pass) are kept in memory only. Existing step compilers are unchanged (`register_step`); plan steps register with `register_plan_step`.
- **The tail reuses the Phase 10 machinery.** `replace_background`'s harmonize pass is the inpaint graph over the local step's seam-band `mask` output, with `MaskPrep(image="p11:local:image", mask="p11:local:mask", grow=8, blur=8, crop=True, padding=64)`: `prepare`/`stitch` keep every pixel outside the band byte-exact. No new engine nodes (S3), and the FakeEngine needed no changes.
- **`replace_background` composites in `p11.media.composite`** (see ADR-0026 for the segmenter): fit/placement geometry, LAB mean/std colour transfer at `colour_match_strength`, edge decontamination (unmixing the background out of partially covered pixels in the feather band), feather, an optional drop shadow, and RGBA output for a flat colour or transparent background. The step's `background_slot` (photo) or `background_colour` is exactly one of; `mask_mode` is `auto` (segment per run), `manual` + `mask_slot`, or `manual` + `mask_png` (a fixed template mask, as for inpaint). All additive: every older schema-v1 document still validates (tested), so no version bump (the ADR-0025 precedent).
**Consequences.** Phase 14 compiles `text_overlay` as a tail-less `LocalStep` the same way (`register_plan_step`, run in `runner._run_local`). A local step's failures map to plain-English problems (`background.segment`, `background.composite`, `input.mask`). The stage's live preview calls the same `run_replace_background` through `POST /api/background/preview`, so the preview is by construction what Apply saves. Cost: `compile()`'s return type changed (callers updated; goldens unchanged for graph steps), and a step's intermediate output is no longer saved to the gallery (only the step's final output, as before for single-graph steps).

## ADR-0026: Subject segmentation: BiRefNet ONNX on the CPU inside P11
**Recorded.** 2026-11-03 09:15 CST (Phase 11)
**Status.** Accepted
**Context.** Background replacement needs a subject mask. R12: prefer a permissively licensed default, with a stronger non-commercial model only as a flagged opt-in; R10: nothing about a model is trusted from memory. The mask is needed (a) live in the Background view ("auto-mask on open, with a spinner"), (b) at job time, and (c) in templates that re-segment each run's subject. The working budget is ~7 GB of VRAM shared with the engine (R5).
**Options considered.** Where it runs: (a) inside the engine (ComfyUI v0.43.0 has core `LoadBackgroundRemovalModel`/`RemoveBackground` nodes loading `Comfy-Org/BiRefNet` safetensors through its VRAM manager), (b) in P11 with ONNX Runtime on the CPU, (c) in P11 with `onnxruntime-gpu`. Which model: (d) `briaai/RMBG-1.4`, (e) `briaai/RMBG-2.0`, (f) BiRefNet (ZhengPeng7, MIT) or its ONNX exports, (g) a 512-px BiRefNet-lite export. All licences, files, sizes and LFS SHA-256 read from the Hugging Face API on 2026-11-03 (07:05–07:30 CST), hashes recomputed over the downloaded files; pre/post-processing read from the repos' `preprocessor_config.json`.
**Measured** (10 P11-generated subjects at 1024×1024, i7-9750H CPU only; `scripts/bench/background_tune.py`, `~/.cache/p11/bench/background/segment.json`):
- `onnx-community/BiRefNet_lite-ONNX` (`birefnet-lite`, 224 MB, MIT): **8.7–11.9 s per image, mean 9.7 s** (six intra-op threads; 7.3–8 s when idle).
- `onnx-community/BiRefNet-ONNX` (`birefnet`, 973 MB, MIT): **17.9–25.1 s, mean 19.7 s** — and its masks agree with the lite model's at **IoU 0.995 mean (min 0.985)** on the 10 subjects: no measurable quality gain for 2× the time and 4× the size.
- Mask quality: on a synthetic product fixture with an exact ground truth the lite model reaches **IoU 0.979** (`tests/gpu/test_background_gpu.py`, threshold 0.85); visually all 10 generated subjects (4 portraits, 6 products) cut out cleanly (contact grids in `~/.cache/p11/bench/background/grids/`). A chroma-key ground truth on generated green-screen images was tried first and **rejected**: the generator does not emit a flat green backdrop (it renders green rooms), so those IoU numbers measure the ground truth, not the masks.
- `briaai/RMBG-1.4` ONNX (176 MB): fast (1.1–1.7 s) but its licence is BRIA's own ("for non-commercial use", commercial by agreement — README and licence link read at the source), and it failed one of the five probe images (nearly the whole scene selected). RMBG-2.0 is CC-BY-NC-4.0 **and gated** (login required), so it cannot be hash-pinned in the manifest (H2) — documented as an optional extra only.
- A 512-px BiRefNet-lite export (`studioludens/birefnet-lite-512`, 2.5 s) failed a probe image outright (empty mask on an interior scene). `cyberagent/layerd-birefnet` (Apache-2.0) ships no ONNX.
**Decision.**
- **(b)+(f) P11-side ONNX on the CPU: `birefnet-lite` in the default set, `birefnet` (full) as the `full`-set quality option**, both MIT, hash-pinned, loaded through `p11.media.segment` (one cached session per model, six threads). CPU means segmentation never takes VRAM, so it is never resident with the engine at all — the R5 worry disappears instead of being managed — and the Background view works with the engine stopped. `p11 serve --fake` and tests use `StubSegmenter`; missing models raise a plain-English "Install it with `p11 models install …`".
- **The default set grew 14.41 GB → 14.63 GB** (H1 allows 30 GB). This is loud, not silent: it is recorded here, in the manifest entry's notes, in the Phase Log and the benchmarks, and flagged for the owner's Phase 17 review. Appendix B counts background replacement in the daily workflow, so the default install must be able to run it.
**Consequences.** Masks take ~7–12 s per image on the CPU (a spinner covers it; the stage's preview reuses the uploaded mask). If the owner finds that too slow, the recorded fallback is the engine-side core nodes (option (a), `Comfy-Org/BiRefNet` safetensors, no custom node needed — S3 clean) or `onnxruntime-gpu` with the GPU lock (measured 1.2 s warm earlier, but it competes with the engine for VRAM and needs the CUDA wheels). The stronger non-commercial models stay out of the default path (R12). **Memory:** ONNX Runtime's CPU arena kept ~12 GB resident after one run; P11 creates sessions with `enable_cpu_mem_arena = False` (peak 6.6 GB during a run, released after it, same speed; measured 2026-11-03 09:30 CST), so a long-running Studio does not hold that memory between masks.

## ADR-0028: Face detection, swap and restore run in P11 on the CPU (resolves ADR-0011)
**Recorded.** 2026-11-03 11:05 CST (Phase 12)
**Status.** Accepted
**Context.** ADR-0011 left the face-swap engine to be decided here: the ReActor ComfyUI node or the FaceFusion headless CLI. R11/S3/S4/S5 bound the choice: models hash-pinned and loadable only in safe formats, no custom node without an ADR and a reviewed source, the NSFW target guard on every swap, and quality/speed measured on the 8 GB laptop. Its own NSFW check downloads `AdamCodd/vit-base-nsfw-detector` **at run time** from `main` with a fixed threshold of 0.979 (its `scripts/reactor_sfw.py`), i.e. an unpinned model and an unreviewed threshold. It wraps the same InsightFace swapper weights, so the licence situation is unchanged.

The face models live in the new **`face` set** (also in `full`), never in `default`.

The non-commercial InsightFace entries require an explicit licence acknowledgement on install (`p11 models install face --accept-licences`), and THIRD_PARTY_NOTICES and the Models list say so. Phase 13's video pipeline reuses exactly this module per frame. If face quality ever needs more than `inswapper_128`, the recorded path is FaceFusion's `hyperswap` models (its `models-3.3.0`) behind the same interface — that is a manifest entry and a model ID change, not an architecture change.

## ADR-0029: The S5 NSFW target guard: two pinned classifiers, fixed thresholds, fail closed
**Recorded.** 2026-11-03 11:05 CST (Phase 12)
**Status.** Accepted
**Context.** S5/ADR-0005: generation is unfiltered, but every face-swap path must refuse sexual or nude targets, with no setting, flag, env var or API parameter that turns it off. The guard must run whatever the source of the job (UI, API, template, and later video frames), and it must not be a single vendor's opinion of what is explicit.
**Options considered.** (a) One classifier (which one: Marqo's ViT-tiny, Freepik's EVA02, `AdamCodd/vit-base-nsfw-detector`, `Falconsai/nsfw_image_detection`); (b) FaceFusion's three-model ensemble (`nsfw_1` YOLO-based EraX, `nsfw_2` Marqo, `nsfw_3` Freepik); (c) an engine-side detector (ComfyUI has none at the pin).
**Decision.**
- **Two classifiers, both required, either one refusing is enough** (`p11.media.nsfw`): `nsfw-marqo-384` (Marqo/nsfw-image-detection-384, Apache-2.0, ViT-tiny 384; unsafe when P(NSFW) ≥ 0.5) and `nsfw-freepik-eva02` (Freepik/nsfw_image_detector, MIT, EVA02 448; unsafe when P(medium)+P(high) ≥ 0.5, the card's own "medium or higher" rule). Both are FaceFusion's ONNX exports from `facefusion/models-3.3.0`, hash-pinned. Marqo's card reports 98.56 % on its 20 000-image test set; Freepik's reports 97–99.9 % per class and 96–100 % on AI-generated content, which is what P11 swaps faces onto.
- **The thresholds are constants** in the module, along with the model IDs; there is no field in any schema, no setting, no env var and no route parameter that names the guard. A test greps the code for one (`tests/unit/test_media_faces.py`), and `tests/unit/test_recipe_model.py` still asserts `FaceSwap` has no guard field.
- **Fail closed.** If either classifier is missing or unreadable, the swap is refused with "install them with `p11 models install face`" (`GuardUnavailable`) instead of running unguarded.
- **Checked twice.** The target is classified before anything else happens in the swap and again on the result, and `Runner.validate` refuses at submit time whenever the target is already a file (an upload, a gallery image or `source_image`) so the user gets a 422 before queueing. A target that only exists after an earlier step is checked when it does.
- **Neutral message, no hints:** "P11 does not put faces onto nude or sexual images. Choose a different image." (and one for the result).
**Consequences.** ~0.7 s per check on the CPU, on both the target and the result of every face swap. The guard's own fixtures are synthetic and non-explicit (a magenta-corner image for the stub, P11-generated portraits for the real classifiers); no explicit image is ever stored in the repo or in fixtures (S6). Phase 13 calls the same `check_target` per video frame (it may classify one frame per second to keep the cost sane; that is its decision to record). Recorded risk: a classifier can miss something; the two-model OR rule and the second check on the result are the mitigations, and the refusal is deliberately irreversible from inside P11.

- **The maps are made in P11 on the CPU** (`p11.media.control`, `p11.media.pose`), as a `GraphInput.transform` the runner applies before uploading: `pose` reads a body skeleton out of a photo (DWPose `yolox-l` + `dw-ll-ucoco-384`, both Apache-2.0, hash-pinned) or takes the pose editor's drawing as-is, `depth` runs Depth Anything V2 Small (ONNX, Apache-2.0, 99 MB), `canny` is OpenCV Canny(100, 200). Preprocessing is optional per step (`Pose.preprocess`), so the editor's rendered skeleton is used unchanged.
- **The skeleton picture is OpenPose-18**, drawn with the standard limb colours and 60 % limb dim (`draw_bodypose` convention, controlnet_aux/DWPose, Apache-2.0, read 2026-11-03 10:14 CST), so what the editor shows is what the ControlNet sees.
**Consequences.** Controls cost 2.5 GB of disk and load into the engine's VRAM only while a pose step runs. The pose editor is client-side SVG (drag joints, mirror, five stock poses) and renders through `POST /api/pose/render`. Measured: a 1024² generation with the union ControlNet runs in the same ~14 s band as without it (no OOM at the default preset); DWPose extraction takes 0.3–0.9 s per picture. If the union ProMax is ever too heavy, the recorded fallback is Xinsir's smaller `diffusion_pytorch_model.safetensors` (2.51 GB) or a single-control SDXL ControlNet — same graph, different manifest ID.

## ADR-0031: IP-Adapter through P11's own node pack (`p11_ipadapter`)
**Recorded.** 2026-11-03 11:05 CST (Phase 12)
**Status.** Accepted
**Context.** "Use as reference" needs IP-Adapter: the generation attends to tokens from a reference image in addition to the text. **ComfyUI v0.43.0 ships no IP-Adapter node at all** (checked: `grep -ri ipadapter` over the pinned checkout returns nothing; `IPAdapterModelLoader` and friends are gone), while the two established node packs (`cubiq/ComfyUI_IPAdapter_plus`, GPL-3.0, last push 2025-04; the older core support) are exactly the third-party code S3 says to avoid unless necessary.
**Options considered.** (a) Add `ComfyUI_IPAdapter_plus` as a pinned custom node (GPL-3.0 code inside an MIT project, needs a source review and a dependency set); (b) implement IP-Adapter as a **custom node P11 owns**; (c) emulate a reference with a ControlNet (tile/repaint) — not the same thing and visibly worse; (d) drop the feature.
**Decision.** **(b)**: `engine/custom_nodes/p11_ipadapter/__init__.py`, P11's own source under the project's MIT licence, installed by `scripts/engine_setup.sh` into the engine's `custom_nodes/` and the **only** pack ComfyUI is allowed to load (`--disable-all-custom-nodes --whitelist-custom-nodes p11_ipadapter` in the pinned launch flags). The lock file records the pack's name, source and the SHA-256 of its entry file; `engine_setup.sh` refuses to install a copy whose digest differs. Two nodes: `P11IPAdapterLoader` (reads `ipadapter/*.safetensors`) and `P11IPAdapterApply` (projects the reference image's CLIP-ViT-H features to 16 cross-attention tokens and patches every cross-attention layer).
- **The checkpoint layout was read from the files** (both `ip-adapter-plus_sdxl_vit-h.safetensors` and `ip-adapter-plus-face_sdxl_vit-h.safetensors`, h94/IP-Adapter, Apache-2.0, hash-pinned): a 16-token Perceiver resampler (`latents [1,16,1280]`, `proj_in`, four attention+MLP layers, `proj_out [2048,1280]`, `norm_out`) over CLIP-ViT-H penultimate states, plus `ip_adapter.<N>.{to_k_ip,to_v_ip}` for 70 cross-attention layers.
- **The layer mapping is derived, not hard-coded:** the `ip_adapter.N` keys follow the UNet's module order **input blocks → output blocks → middle block**. That was established from the checkpoint's own widths (640×4, 1280×50, 640×6, 1280×10) against a walk of the real SDXL UNet at the pin (70 layers, widths 640×4, 1280×60, 640×6 — only the input/output/middle order reproduces the checkpoint's split). The node walks the engine's UNet at apply time and **checks every layer's width against the checkpoint's**, refusing to run on a mismatch instead of producing a wrong picture.
**Consequences.** The reference path is `CLIPVisionLoader` + `CLIPVisionEncode` (core) → `P11IPAdapterApply` (ours). Two models ship: `ip-adapter-plus-sdxl` (style and composition) and `ip-adapter-plus-face-sdxl` (the person), plus the 2.5 GB `clip-vit-h-14-encoder`; all in the `control` set. The face-**ID** variant is not shipped: it needs an InsightFace embedding model whose weights are non-commercial (ADR-0028), and the plus-face checkpoint already keeps a person recognisable — recorded as an optional extra if the owner wants it. Cost: one small module (~330 lines) that must follow ComfyUI's attention-patch API across engine bumps (the pin makes that a reviewed diff).

## ADR-0032: Additive schema changes for face, pose and reference
**Recorded.** 2026-11-03 11:05 CST (Phase 12)
**Status.** Accepted
**Context.** Schema v1 (ADR-0007) fixed the step union in Phase 04 and named `face_swap`, `pose` and `reference` with their fields. Phase 12 needed three small additions the earlier schema did not cover, and the manifest needed room for the new model kinds and sets (Phase 06's `facedetect` kind was added the same way).
**Decision.**
- **`FaceSwap.blend: Unit = 1.0`** (how much of the swapped face is pasted in) — the UI's "Blend" slider; `restore_visibility` already covered the restore strength.
- **`Pose.control: Literal["openpose", "depth", "canny"] = "openpose"`** — the union ControlNet's type (ADR-0030).
- **A new step type `face_restore`** (`image_slot`, `face_index`, `restore_model`, `visibility`), so "Restore faces" is a real one-click action instead of a swap onto itself.

**Consequences.** `tests/unit/test_recipe_model.py` covers the new members; `PROVISIONAL_DEFAULT_SET` (the compiler's pure registry) grew by the 13 new models and is asserted equal to the manifest. ## ADR-0033: Video face-swap: CPU face path per frame, ffmpeg extract/stitch, resumable job rows
**Recorded.** 2026-11-03 14:08 CST (Phase 13)
**Status.** Accepted
**Context.** R13 asks for probe → extract → swap in batches → optional restore → re-encode with the original audio, with progress, cancel, resume after a crash and scratch cleanup. The prompt's "through the engine (or FaceFusion CLI, per ADR-0011)" predates ADR-0028, which decided that faces are P11's own CPU pipeline; the video path reuses that module per frame so one implementation and one guard cover images and video.
**Decision.**
- **Per-frame swaps call `p11.media.faces.run_face_swap` unchanged.** The S5 guard therefore runs inside every swapped frame (ADR-0029) with no video-specific code path that could forget it (ADR-0034). Frame extraction and stitching are the system ffmpeg (n9.0.2 on the reference laptop, recorded), always argument lists, never shell strings (S8); rotation is honoured by auto-rotate on decode and the output is H.264 yuv420p at the source frame rate with the audio copied when the codec fits MP4 and re-encoded to AAC when it does not.
- **Video jobs are job rows of their own kind** (`jobs.db` migration v2: `kind`, `spec` columns): the recipe compiler has no video output, so the pipeline lives in `src/p11/jobs/video.py` behind `JobQueue.submit_video`/`resume_video`. The queue's single worker still runs one job at a time (R24): a video job holds no GPU lock because it uses no GPU, and it skips the engine start entirely.
- **Resume is per frame.** The scratch dir `~/.cache/p11/jobs/<job>/` holds the frames; `<job>.json` (outside it) records the stage, the frame count and the last finished frame, saved after every frame. A crash keeps both; a **user** cancel deletes the scratch frames unless "keep frames" is set (`JobControl.cancel(purge=True)`), and a shutdown never purges, so an interrupted run is always resumable. A resume re-checks the spec's hash (`render_hash`, which ignores `resume_of`/`keep_frames`/`confirm_limits`) so two different settings can never mix, and continues at the first unfinished frame without redoing finished ones.
- **Quality presets** are `fast` (no GFPGAN, 720p cap, CRF 23) and `good` (restore, full size, CRF 18); the user can override the frame-size cap, trim the clip, opt into temporal smoothing (blend of the face region with the previous output where the tracked box barely moved) and "keep frames". R13's 60 s / 1080p defaults warn with a rough time estimate and need an explicit confirmation (`confirm_limits`), enforced at submit and again in the job.
- **The finished video** goes to the R7 layout as `.mp4` with a JSON sidecar (the run record's video equivalent) and is served by `/api/video/jobs/{id}/file` with Range support for the player. It does **not** enter the gallery index, which is image-only in v1.
**Consequences.** `Job.summary` carries `kind`; `/api/jobs` shows video jobs alongside generations. A swap is seconds of CPU per frame (measured in `docs/P11_BENCHMARKS.md`), so a 30 s clip is tens of minutes — the UI shows frame progress and an ETA, and the limits confirmation names the estimate. The video path needs ffmpeg at run time (`p11 doctor` and the installer already name it).

## ADR-0034: The S5 guard on video: every swapped frame plus a sampled pre-pass, no switch
**Recorded.** 2026-11-03 14:08 CST (Phase 13)
**Status.** Accepted
**Context.** S5 keeps the NSFW target check on video face-swap. The Phase 12 results recorded "one sampled frame per second" as the option for clips, with the requirement that the guard run for every frame the pipeline swaps and that the choice and its risk be stated.
**Decision.**
- **Every swapped frame is guarded twice, in code that already exists:** `run_face_swap` classifies the target frame before the swap and the result before it is written (ADR-0029) — for video, once per frame. Nothing in the video path can bypass it: the pipeline only swaps through that function.
- **A sampled pre-pass refuses the whole clip before any swapping**: about one frame per second plus every detected scene change (a 32x32 thumbnail difference) goes through `check_target` first, so a bad clip fails in seconds instead of after an hour of CPU work. A refusal stops the job and deletes its scratch frames (S6).
- **No switch** exists anywhere (the module constants of `p11/media/nsfw.py` are the only thresholds); the guard fails closed when a classifier is missing.
**Consequences.** The guard costs about 1.4 s per frame on the CPU (two classifier runs), measured in the benchmarks — the recorded cost of covering every frame. **Risk, stated:** two classifiers at fixed thresholds can still miss a frame (the residual risk Phase 12 recorded for still images applies to frames too), and a clip that passes the sampled pre-pass can contain an unsafe moment between samples — which the per-frame check then catches at swap time. Sampling exists only for fail-fast behaviour; it never replaces the per-frame check.

## ADR-0035: Text overlay in Pillow, logo exports, Models page operations, optional-step skipping
**Recorded.** 2026-11-03 17:45 CST (Phase 14)
**Status.** Accepted
**Context.** R23: diffusion models spell logos badly, so exact text is drawn by a deterministic step. Phase 11's driver (ADR-0027) already takes local steps. Phase 14 also needs a Models page over the Phase 06 manager and logo helpers.
**Options considered.** Text: (a) draw in Pillow as a `LocalStep`, (b) a ComfyUI text node (custom node, S3), (c) draw in the browser. Fonts: (d) bundle five OFL families, (e) system fonts. Models page: (f) mirror `p11 models` as API routes with event-stream progress, (g) shell out to the CLI. Optional inputs: (h) skip a step whose optional image slot is empty, (i) require the slot.
**Decision.**
- **(a)** `text_overlay` compiles to a tail-less `LocalStep` (`recipe/steps/text_overlay.py`) and `p11.media.text` draws it at full resolution (auto-fit by binary search to the printable box, multi-line, alignment, 9-way anchor or a dragged `x`/`y`, letter spacing, outline, soft shadow, vertical gradient). `TextOverlay` grows additively (`weight`, `colour2`, `align`, `x`, `y`, `letter_spacing`): no schema bump. An empty optional text slot, or "let the model try the text" (`also_prompt_model`), compiles to no item; the compiler's `previous` pointer only advances when a step produced an item.
- **(d)** Five Google Fonts families under the SIL OFL 1.1 in `assets/fonts/` (Inter, Space Grotesk, Playfair Display, Bebas Neue, JetBrains Mono), each with its licence text and a `fonts.json` entry holding source, SHA-256 and check timestamp (2026-11-03 17:00 CST); a test checks hashes and licence files.
- **(f)** `/api/models/plan|install|verify|add|licences|operations`, `POST /api/models/{id}/enabled` and `DELETE /api/models/{id}`. Install runs in a worker thread and publishes `models` events (label, bytes done/total); one install at a time. The acknowledgement dialog shows each licence and the commercial flag, and the request carries `accept_licences`.
- **(h)** `FaceSwap` is `skippable_if_unbound`: when its image slots name an optional slot the run left empty, the step is dropped (this is how the avatar starter's optional face works).
- Logo pack (`POST /api/images/{id}/logo-export`): transparent cut-out through Phase 11's segmentation, else a flat-colour key from the border colour; square PNGs at 512/256/128/64/32 and `favicon.ico` in one ZIP.
- A test-only hook, `P11_ALLOW_LOOPBACK_MANIFEST=1`, lets the manifest and downloader accept `http://127.0.0.1` so the Playwright Models walkthrough installs a 22-byte fixture from a local server. It cannot allow any other host.
**Quality chain (ADR-0010).** Measured on the laptop (warm, performance profile, `tests/gpu/test_quality_upscale_gpu.py`): Speed 15.8 s at 1920x1080 and 16.5 s at 2560x1440; Quality (`latent`) 34.9 s and 76.6 s, no OOM. `latent` stays the Quality chain: it is the faster of the two refinement chains in Phase 03's measurements (`both` was 55 / 88 s) and fits the VRAM budget. I did not redo a by-eye `latent` versus `both` comparison in this phase, so the choice rests on time and memory plus Phase 03's contact sheet.
**Consequences.** Logo starters carry a `logo_text` slot and lose the `mark-only` tag; existing users keep their old copies because of the starter marker (user guide). Phase 16 re-runs the action counts. Left as follow-ups: 3D-avatar prompt/LoRA tuning and the 10-prompt defaults review (Phase 14 Phase Log).
